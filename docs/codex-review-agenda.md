# 验收对账清单：Codex 交付后要对的点

写于 2026-08-12，**在 Codex 开工之前**。配套 [codex-goal.md](codex-goal.md)。

## 为什么现在就写

因为事后写没用。等成品出来再列「哪里可能有问题」，我会不自觉地照着已经做出来的东西找理由 —— 做出来什么就觉得什么合理。**先把预测写死，再拿现实去对**，才分得清「这个决策是对的」和「这个决策我懒得改了」。

下面每一条都是我现在的预测。到时候逐条打勾：预测对了就按预案处理，预测错了也记一笔 —— 那说明我对这个项目的某个判断需要修正。

**「改起来贵不贵」这一列比结论更重要。** 便宜的错误不值得现在纠结，贵的错误值得在他动手前就再想一遍。

## A. 我替你定的决策里，你最可能不同意的

### A1. 估值 KV 存 7 天 —— 你会看到「3 天前的估值」

**我怎么定的**：TTL 从 60 秒改成 7 天。理由是陈旧度该由展示层根据 `estTime` 判断，不该由存储层用过期代劳。

**你大概会问**：周一早上打开 App，看到上周五的估值挂在那儿，这不是误导吗？还不如不显示。

**我的预案**：这条成立与否**完全取决于前端有没有把陈旧度显示出来**。标了，它就是「上次收盘时的估算」，有用；没标，它就是骗人，那 7 天 TTL 就是纯粹的坏决定，比 60 秒还坏。所以这条要和前端一起验，不能单看后端。

**怎么验**：非交易时段打开持仓页，看估值旁边有没有明确的时间标注。没有就是我错了 —— 但改的是前端（加标注），不是把 TTL 改回 60 秒。

**改起来**：便宜。一个常量。

### A2. 不做密码，靠邀请码 + 恢复码

**我怎么定的**：没有密码，兑换邀请码即建号发 cookie，一次性给一个恢复码用于换设备。

**你大概会问**：恢复码丢了怎么办？就永久失去账号？以及 cookie 90 天过期后是不是要重新兑换？

**我的预案**：恢复码丢失 = 你自己进 D1 手工重置 `recovery_hash`。因为是自己的库，这条路一直在。真正要确认的是**兑换页有没有强制用户确认「我已保存」** —— 只是显示一下就跳走的话，丢失率会接近 100%。

**改起来**：现在改便宜（还没有真实用户）。有用户之后加密码 = 要做迁移，贵。**这是本清单里最值得在他动手前再想一遍的一条。**

### A3. 邀请码手工插 D1，不做生成接口

**你大概会问**：我每想加一个人就要跑一次 wrangler 命令？

**我的预案**：是的，故意的。这是唯一的准入闸门，开自助入口等于没有闸门。如果嫌烦，折中方案是做一个需要登录且只有你的 user_id 能用的生成接口 —— 但那要先有「管理员」概念，是新的一层。

**改起来**：中等。加接口容易，加权限模型麻烦。

### A4. `/api/quotes` 要登录，公开页面走专用受限路由

**你大概会问**：为什么要多一条路由？直接让 quotes 公开不行吗？

**我的预案**：不行 —— `/api/quotes?secids=` 接受任意 secid，公开就等于给全世界提供一个免费行情 API，而这个项目本来就在小心翼翼地控制上游请求量（P0 那 30 小时探针测的就是这件事）。专用路由只返回某只基金重仓股的行情，滥用面是有限的。

**改起来**：便宜，趁早定。

### A5. 验收池从 10 只变成 11 只

**你大概会问**：roadmap 白纸黑字写的是「选 10 只基金（2 ETF、3 指数、5 主动）」，为什么变了？

**我的预案**：因为那 3 只「指数」全是 ETF 联接，而被动分支有两条完全不同的算法，另一条一个样本都没有。加第 11 只而不是替换，是为了不断掉已有样本的连续性。如果你觉得该守住 10 这个数，那就替换掉一只联接 —— 代价是那只从明天起断档。

**改起来**：便宜。

## B. Codex 大概率会做偏的地方（这几条一定要逐个核对）

### B1. `NONE` 有没有真的分成两类 ★ 最重要

**为什么担心**：这是整个交付里最容易「看起来做了其实没做」的一条。他很可能加一个计数字段就算完成，但真正的要求是：**缺输入型的 `NONE` 出现一只就要 warn，而结构性的（QDII/债/货）永远不 warn**。两者混在一起，告警就永远不会响 —— 因为债基天天都是 `NONE`。

**怎么验**：不要读代码，制造一次故障。挑一只场外基金，手工把它在 `latest_official_navs` 里的行删掉，等下一个分钟周期，看日志有没有 warn：

```
npx wrangler d1 execute lookthru --remote -c .wrangler.generated.toml \
  --command "DELETE FROM latest_official_navs WHERE fund_code='005827';"
npx wrangler tail
```

没 warn 就是没做到，不管代码写得多漂亮。（验完等当晚 19:30 会自动补回来。）

**改起来**：便宜，但**不改的代价极高** —— 这一条是后面所有验收数据可信度的地基。

### B2. 告警去重的粒度

**为什么担心**：我在 goal 文档里定的是「基金代码 + 错误类别 + 日期」，但「按天去重」这个说法很容易被实现成只按日期。那样的话 A 基金上午坏了之后，B 基金下午坏掉会被静默吞掉。

**怎么验**：直接看 alert key 是怎么拼的。key 里没有基金代码就是做偏了。

**改起来**：便宜。

### B3. 分红的成本口径

**为什么担心**：我这次在 goal 文档里定死了五种类型的表，但**现金分红不增加成本、红利再投也不增加成本**这条反直觉 —— 很容易被实现成「再投 = 按当日净值买入」，那样成本就凭空长了，持仓收益率会永久性偏低，而且没有任何地方会报错。

**怎么验**：看单测有没有覆盖 DIVIDEND 的两种形态。没有就补，这是纯逻辑，测起来很便宜。

**改起来**：代码便宜。但如果已经录了真实流水才发现，要重算历史，麻烦。

### B4. 穿透里「基金持仓市值」到底用了估值还是官方净值

**为什么担心**：我要求了「用了哪个要在 meta 里标明」，但**没定默认用哪个** —— 这是我留的口子。他大概率会一律用官方净值（简单），结果就是盘中打开穿透页，数字一整天不动。

**怎么验**：盘中和盘后各打一次 `/api/xray`，看敞口金额有没有变化，以及 meta 里标的是什么。

**我的倾向**：盘中有估值就用估值，没有就退回官方净值，两种情况 meta 都要如实标。

**改起来**：便宜。

### B5. 误差报表有没有被 15:05 的收盘行污染

**为什么担心**：我要求 15:05 也落 D1（否则那个任务不产生任何存活超过一分钟的东西），同时要求报表**默认只用 14:55 那批**。这两条要一起做对才行。他很可能落了库但报表把两批一起算了 —— 那样误差会莫名其妙变小（收盘价离当日净值当然更近），而且看起来像是估值精度提升了。

**怎么验**：
```
npx wrangler d1 execute lookthru --remote -c .wrangler.generated.toml \
  --command "SELECT trade_date, COUNT(*) FROM valuation_samples GROUP BY trade_date ORDER BY trade_date DESC LIMIT 5;"
```
每个交易日应该是 22 行（11 只 × 2 批），而报表的样本数应该是 11。对不上就是混算了。

**改起来**：便宜。但**不发现的话会让人误以为估值精度达标**，属于会骗到自己的那类错误。

### B6. 「按天去重」和「整批全失败仍要抛」会不会打架

**为什么担心**：这是我给的两条规则的交界处，我没说清优先级。整批全失败也是「同一天同一类错误」，按去重逻辑第二次就不抛了。

**我的意图**：整批全失败每次都要抛，不参与去重 —— 那是「系统性坏了」而不是「某只基金坏了」。

**怎么验**：问他怎么处理的，或者看代码里这两条的先后。

**改起来**：便宜。

### B7. 他到底碰没碰前端

**为什么担心**：`/goal` 模式要求「做出成品」，而成品的自然定义包含界面能用。我在 goal 文档里写了「前端归 Claude，默认你不用碰」，但他为了闭环很可能还是去接了。

**怎么验**：`git log --stat` 看有没有 `apps/web/` 的改动。

**如果他碰了**：不要直接回滚 —— 先按 [frontend.md](frontend.md) 的 9 条 UI 不变量逐条验，尤其 #1（估算与官方净值视觉可分）、#5（延时行情不能当实时）、#7（有缓存不要换骨架屏）、#8（空态/加载态/陈旧态是三件事）。这四条是接数据时最容易破的。守住了就留着，破了再说。

**改起来**：如果他破了不变量，重做界面比改后端贵得多。这是本清单里**协作成本最高**的一条。

### B8. Discord 发送成功的判定

**为什么担心**：Discord webhook 成功返回的是 **`204 No Content`**，不是 200。判定写成 `status === 200` 的话，每一次成功都会被记成失败 —— 然后触发 22:00 补发，于是每天收到两条一样的日报。两周之内你就会静音这个渠道，那时真出事的告警也一起被静音了。

反过来也一样坏：如果他把任何响应都当成功，那 webhook 失效之后你会**一直以为日报在正常发**，而实际上什么都没到。

**怎么验**：不要读代码，用一个失效的 webhook URL 实际跑一次，确认它被判成失败并且补发真的触发。这条我已经写进 goal 文档的验收要求里了，但**这是那种「他说验过了」和「真的验过了」很难区分的项** —— 让他把那次失败的日志贴出来。

**改起来**：便宜。但发现得晚的话，中间那段时间的日报可信度是零。

## C. 数据出来会打脸的（不是 bug，是预期管理）

### C1. `MEDIUM < 0.6%` 大概率达不到

**为什么**：MEDIUM 档是主动基金，算法是「前十大重仓股的实际涨跌 + 剩余仓位按基准补足」。而前十大只覆盖净值的 40–70%，也就是说**有三到六成的仓位是拿沪深300 猜的**。0.6% 这个数当初是拍的，没有实测依据。

**届时的讨论**：roadmap 写着「达不到就调阈值 —— 不要调 UI 去掩盖」。所以问题不是要不要调，是调到多少算诚实。**我的建议是先跑满 10 个交易日再调**，用实测的 p90 当新阈值，而不是用「刚好让现在这批数据通过」的数。后者是在用一次抽样定标准。

**这条我预测会发生的概率：高。**

### C2. `EXACT` 档的误差可能比 `HIGH` 还大

**为什么**：场内 ETF 的 `estNav` 是成交价、官方 NAV 是净值，两者差一个折溢价。所以 `EXACT`（名字听起来最准）在报表里的数字可能最难看。

**这不是 bug**，是量纲不同 —— 我已经要求报表把它单独成档并标明。但第一次看到还是会觉得刺眼，先有个预期。

### C3. 请求量和成本

**为什么**：分钟估值 cron 是每交易日 360 次 invocation（其中约 118 次是空跑），加上鉴权之后每个 API 请求还要多一次 session 查询。Workers Paid 扛得住，但值得在第一个完整月之后看一眼实际用量。

**届时的讨论**：那 118 次空跑能不能省掉（cron 表达式收窄）。现在不用动，这是优化不是修复。

## D. 协作边界

### D1. `packages/shared` 的类型形状

我在 goal 文档里写了「不要改已有类型的形状」。如果他改了，前端会全线崩 —— 而且我并行做的前端工作会白做。

**怎么验**：`git diff <他开工前的 commit> -- packages/shared/` 应该只有新增，没有改动或删除。

### D2. `Position` 类型已经定好了接口契约

`packages/shared/src/index.ts` 里的 `Position` 已经带了 `valuation` 字段（`Valuation | null`）和 `dayReturn`，注释也写明了「盘中估算，与官方口径严格分离」。**这就是 `/api/positions` 该返回的形状**，他不需要发明新的，我也会照它接前端。如果最后两边对不上，先看是谁偏离了这个已有的类型。

## 如果只来得及核对三件事

1. **B1** —— 缺输入型 `NONE` 会不会 warn。制造一次故障实测，别读代码。这是所有验收数据可信度的地基。
2. **B7** —— 他碰没碰前端；碰了的话 UI 不变量守住没有。这条的返工成本最高。
3. **A2** —— 恢复码的保存流程。趁还没有真实用户，这是最后一次便宜地改动账号体系的机会。
