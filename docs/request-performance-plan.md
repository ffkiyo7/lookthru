# 基金搜索与详情请求性能计划

## 目标与边界

本轮解决基金搜索候选约 20 秒、基金详情约 5 秒的长尾等待，同时保留数据来源、抓取时间、延时与陈旧标记，不用隐藏旧数据的方式伪装实时。

用户已经确认以下产品边界：

- 搜索候选不再等待页面没有展示的涨跌幅补全。
- 详情页继续等基金资料、持仓披露和行情整组数据准备完毕后一次展示；不拆成分段出现，不改布局、间距、配色、组件 API 或信息层级。
- 行情、持仓与基金资料允许先返回 last-known-good，再在后台刷新；旧值必须携带实际抓取时间和陈旧/延时状态。
- 复用分钟估值 Cron 已经集中抓取的行情，避免用户请求再次打同一上游。
- 不新增 npm 依赖，不引入 Durable Object、Queue 或新的缓存系统。

## 当前根因

### 搜索

`/api/funds/search` 取得搜索候选后，会同步读取或抓取每只候选的新浪涨跌幅。搜索页没有展示这些字段，但缓存每 60 秒失效，上游单次超时 12 秒且默认会重试，因此一次抖动会把候选响应放大到 15–20 秒。

### 详情

详情页分别请求精确代码搜索、持仓和持仓行情。行情接口内部又读取一次相同持仓；60 秒行情缓存未命中时，用户请求同步等待整条多源降级链。生产计时中，冷行情单独需要 6.50–9.36 秒，缓存命中约 0.67 秒。

### 固定请求成本

每条公开基金请求都通过普通 KV 做一次限流读取和写入。KV 冷读需要访问区域或中央存储；详情的三条并发请求会重复支付这项成本。

## 实现方案

### 1. 搜索关键路径

- 搜索响应只保留页面实际消费的基金代码、名称、拼音、类型、官方值及日期。
- 删除搜索请求里的新浪涨跌幅抓取与对应 60 秒缓存实现。
- 前端把 TanStack Query 提供的 `AbortSignal` 传到 `fetch`；输入变化后取消已经过期的搜索请求。
- 搜索候选缓存仍保留 1 小时，缓存写入在响应发出后完成。

### 2. 单一详情接口

- 新增 `/api/funds/:code/detail`，一次返回基金资料、持仓披露和对应股票行情。
- 前端详情页只发一条公开详情请求，但保留原有整页 loading / error / success 分支和一次展示顺序。
- 旧的持仓与行情接口继续复用相同服务实现，避免突然破坏已有调用方；前端不再重复请求它们。

### 3. 行情 stale-while-revalidate

行情按两层存储：

- `quote:{secid}`：60 秒新鲜窗口。
- `quote-lkg:{secid}`：7 天 last-known-good。

读取规则：

1. 新鲜值存在时立即返回。
2. 只有 last-known-good 时立即返回并把该代码加入 `staleSecids`，用 `waitUntil` 后台刷新。
3. 完全没有值时只给上游一个短的前台预算；预算耗尽即返回 `unavailableSecids`，同一次刷新继续在 `waitUntil` 中执行。
4. 上游失败保留旧值，不覆盖、不删除，不把旧值标成实时。

整条行情降级链设置总预算。实时源优先按近期成功与延迟排序；单个失败源进入短暂冷却，避免每次请求都先撞同一条坏链路。延时源仍然排在所有实时源之后，`delayed` 继续传到 UI。

旧行情和旧持仓触发的共享后台刷新按数据键限制为每分钟最多一次，避免同时打开页面的用户各自请求上游。

### 4. Cron 复用

分钟估值任务集中抓到行情后，同时写入 `quote:*` 与 `quote-lkg:*`。真实持仓已包含在估值 universe 中，因此正常交易时段打开自己持有的基金时，应直接读取一分钟内的共享行情，不再产生 per-user 上游请求。

### 5. 持仓本地优先

持仓读取顺序改为：

1. 热 KV；
2. KV last-known-good；
3. R2 `holdings/{code}/latest.json`；
4. 只有本地完全没有数据时，才在前台请求东财。

命中 last-known-good 或 R2 后立即返回，并在后台刷新东财。持仓是否陈旧仍以报告期和来源状态表达，不能因为“刚重新下载过旧季报”就伪装成新披露。

### 6. 非阻塞缓存维护

用户响应所需数据已经取得后，搜索、基金资料、持仓和行情的 KV 写入交给 `waitUntil`。写入失败必须记录原始错误；只是不能让用户为缓存维护继续等待。

### 7. 专用限流

使用 Cloudflare Workers Rate Limiting binding 替换 KV 计数器，保持现有三档额度：

- 公开基金接口：30 次/分钟；
- 邀请码与恢复码：10 次/分钟；
- 公开健康接口：60 次/分钟。

binding 是节点本地、宽松一致的滥用挡板，与当前 KV 限流的产品语义一致，但正常请求不再等待远端 KV 读写。

### 8. PWA 请求策略

- 修正 Workbox 路由正则，使其确实匹配完整的同源 URL。
- 搜索候选使用 stale-while-revalidate，优先返回已访问关键词的缓存，并后台更新。
- 详情相关接口使用 network-first，网络预算从 5 秒缩短到 2 秒；超时后返回已有离线缓存。
- 服务端响应中的 `fetchedAt`、`staleSecids`、`delayed` 仍是数据时效真相，Service Worker 缓存不能覆盖这些口径。

## 验收标准

- 搜索页不再触发新浪涨跌幅请求，接口响应类型不再包含无人消费的涨跌幅字段。
- 详情页只发一个基金详情业务请求，页面仍然整体展示。
- 有 last-known-good 时，行情和持仓接口不等待上游后再响应；后台刷新失败后旧值仍可读且明确标陈旧。
- 分钟估值抓取成功后，详情读取的 `quote:*` 可直接命中。
- 构建后的 `sw.js` 包含可匹配完整 URL 的搜索与详情缓存规则，以及 2 秒 network-first 超时。
- 相关单元测试、全量单元测试、三个 TypeScript project、前端构建全部通过。
- 用生产或等价真实流程分别记录搜索、详情、行情冷/热计时；若未部署，则明确区分本地验证与线上尚未生效，不能把本地结果写成生产事实。

## 实施与验收结果（2026-08-13）

上述 8 项均已实现，详情页仍保留原来的整页 loading / error / success 分支和页面结构。

- TypeScript 三个 project 通过；常规测试 8 个文件、78 项全通过；真实上游契约测试在本机网络下 13/13 通过。
- 生产前端构建通过；生成的 `sw.js` 已核对包含搜索 stale-while-revalidate、详情 2 秒 network-first 规则。
- Wrangler dry-run 成功识别三档公开接口限流、一个共享刷新闸门及全部现有资源。
- 本机权限下用 `wrangler dev` 和真实上游计时：同一 local Worker 会话中，“易方达全球”首次搜索 246ms、随后缓存命中 11ms；首个候选 `012920` 首次详情 283ms、随后缓存命中 8ms。首次详情实际返回 10 条持仓和 3 条可映射实时行情，不是空响应。

这些是本机等价流程的验收值；代码尚未部署，因此不能写成生产延迟。生产侧的最终时延仍受 Cloudflare 出口、KV 热度与已有 Service Worker 更新进度影响，部署后应重新记录一次。
