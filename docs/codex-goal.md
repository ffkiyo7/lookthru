# 交给 Codex 的目标：把 lookthru 从「UI 完整、数据空壳」做成「能用」

制定于 2026-08-12。这份文档覆盖当前**全部**剩余后端工作，写给 `/goal` 模式 —— 给的是目的地和边界，不是分步指令。路线你自己定。

## 什么算做完

一个真实用户能：兑换邀请码登录 → 录入自己的持仓 → 盘中看到带精度标注的估值 → 看到持仓穿透后的股票级敞口 → 每晚 21:00 收到日报。并且**当这条链路的任何一环坏掉时，有人会知道**。

最后半句和前半句同等重要。这个项目已经栽过两次「所有指示灯全绿，系统是死的」（交易日历跨年断崖、估值 8/10 为空但日志报 `valued=10 failed=0`），复盘都在 [roadmap.md](roadmap.md) 里。**不产生信号的正确实现，在这个项目里算没做完。**

## 依赖关系（事实，不是排期）

```
P2 收口 + 误差报表        独立，但验收数据正在产生，越早越好
用户 / 鉴权 / 持仓录入     关键路径 —— 下面三块的共同前置
   ├── 持仓穿透 P5
   ├── Notifier P4
   └── 前端接真实数据
pipelines + 搜索涨跌幅     独立，任何时候都能插
```

**注意 roadmap 的功能编号（P2 → P5 → P4）不是实施顺序。** P5 穿透和 P4 日报都要「用户的持仓」，而 `transactions` 表现在是空的，**且没有任何途径能往里写** —— 没有注册、没有鉴权、没有持仓录入接口，`apps/api/src/` 下也没有任何鉴权代码。所以真正的瓶颈是鉴权那一层，它在 roadmap 里被埋在「还需要建的东西」。

先做 P2 收口的理由不同：它的验收数据从 2026-08-12 晚上开始产生，而其中三条缺陷会让「数据是好的」和「数据是坏的」在日志里长得一模一样。晚修一天就多一天分不清。

## 五条通用判据

这些是从这个项目已经踩过的坑里提炼的。**你遇到我没列举的情况时，按这几条判断**，它们比下面任何一条具体决策都更重要。

1. **能标注的事不要用删除来解决。** 陈旧度是展示层的判断，不该由存储层用过期代劳。数据里带着时间戳，消费方就有能力说「这是 3 分钟前的」；把数据删掉，就把这个能力一起删了。

2. **可用性要测「还剩多少」，不要测「多久前更新的」。** 两者平时相关，恰恰在最危险的场景里反向 —— 定时刷新会一直刷新「更新时间」，而余量在一天天缩短。交易日历那次就是这么差点死掉的。

3. **统计口径必须能区分「算出来了」和「算了但没结果」。** 把空结果计入成功数，就是在制造一个永远不会红的仪表盘。

4. **高频、已知、不可操作的红，会把人训练成无视同一渠道里可操作的红。** 告警要按天去重、要聚合。宁可一天一条能看的，不要一天 242 条没人看的。

5. **fail closed 优于产生一个没人能发现是错的数。** 但 fail closed 必须留下痕迹 —— 静默跳过和成功执行在界面上不能长得一样。

## 不可改的决策

这些不是建议。真觉得某条有问题就停下来说，不要顺手改掉。分组只是为了好找，不代表实施顺序。

### 估值收口（P2 复盘七条的处置）

完整分析在 [roadmap.md 的 P2 复盘](roadmap.md#p2-复盘落地当天发现的七件事)，先读那一节。

- **KV TTL 从 60 秒改成 7 天。** 现值恰好等于刷新间隔，余量为零，任何一次周期变慢接口就返回空对象。7 天能扛过长假；真过期了才是「确实很久没估值了」这个有意义的信号。（判据 1）
- **`CLOSE_SNAPSHOT` 必须落 D1。** 现在它算完就蒸发。15:05 那次也写一行 `valuation_samples`，与 14:55 那批用不同标记区分。**采样时刻仍是 14:55**（验收口径，别动），报表默认只用 14:55 那批。
- **`NONE` 拆成两类分别统计**：结构性不可估（QDII / 债基 / 货基，正常）vs 缺输入（缺前一交易日净值、缺业绩基准、行情全缺 —— 这是故障，一只都不该有，出现就 warn）。（判据 3）
- **失败告警按天去重**，复用 `cron.ts` 里 `logUnavailableCalendarOncePerDay` 那套 `alert:*` 键。仍然要抛的情况：整批全失败。（判据 4）
  **去重粒度是「基金代码 + 错误类别 + 日期」**，不是「日期」。只按日期去重的话，A 基金上午坏了之后，B 基金下午坏掉就被吞掉了 —— 降噪不能降到把新故障也降掉。同一只基金同一类错误一天一条，换了基金或换了错误类别就是新的一条。
- **非联接被动基金要求 `benchmark.weight` 存在且 ≥ 90，否则 fail closed 成 `NONE`。** `danjuan.ts` 的 `symbolToSecid` 只认 `SH`/`SZ`，港股/美股指数进不了候选表，所以「沪深300×50% + 恒生×50%」这类混合基准照样通过唯一性检查；联接分支乘了 `weight` 能自愈，非联接分支会把全部敞口押在一个只占一半的指数上还标 `HIGH`。判据已经解析出来了，用上它。
- **验收池加第 11 只场外非联接被动指数基金，不要替换现有 10 只**（会断掉样本连续性）。选取标准：`isPassiveIndexFund` 真、`isExchangeTradedCode` 假、名称不含「联接」、`fetchFundBenchmark` 返回 `weight ≥ 90`。**先实际跑一次确认再写进 `universe.ts`**，不要凭印象填代码。
- **场内 ETF 在误差报表里单独成档。** 场内 `estNav` 是成交价、`prevNav` 是官方净值，量纲不同（其余分支都满足 `estNav = prevNav × (1+estChgPct/100)`，只有这支不满足），直接相比测到的是**折溢价**不是估值误差。**不要为了让数字好看去调 `EXACT` 阈值** —— roadmap 明说「不要调 UI 去掩盖」，调阈值是同一件事的变体。
- **误差报表**：`valuation_samples` 已有 `official_nav` / `official_nav_date` / `reconciled_at` 列，`nav/sync.ts` 也已在回填，所以这只是个读查询，不需要新写路径。按 precision 分档给样本数、平均绝对误差、p50、p90、超阈值只数；阈值 `HIGH < 0.15%`、`MEDIUM < 0.6%`。

### 鉴权与持仓

`users` / `transactions` / `positions_cache` 三张表已建（`apps/api/migrations/0002_data_layer.sql`），`Transaction` / `Position` 的 zod 类型已在 `packages/shared/src/index.ts` 就位。缺的是这三者之间的一切。

- **不做密码。** 邀请码兑换 → 直接建用户 + 发会话。这是个小圈子工具，密码只带来找回流程、强度校验、泄露面三样负担，换不来任何东西。
- **会话用 HttpOnly cookie，D1 里只存 token 的 SHA-256 哈希。** token 是 32 字节随机数的 base64url，cookie 属性 `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=7776000`。只存哈希是为了 D1 万一泄露时攻击者签不出可用 cookie。
- **兑换时一次性返回「恢复码」**（同样只存哈希），用于换设备。之后任何接口都不再吐出它。
- **邀请码手工插 D1，不做生成接口。** 这是唯一的准入闸门，不要给它开自助入口。
- **鉴权边界照这张表，不要自由发挥：**

  | 路由 | 需要登录 | 理由 |
  |---|---|---|
  | `GET /api/health`、`GET /api/probe/stats` | 否 | `/probe` 是公开面板 |
  | `POST /api/probe/run` | **是** | 会触发上游抓取 |
  | `GET /api/funds/search`、`/api/funds/:code/*` | 否 | 未登录也要能搜和看详情 |
  | `GET /api/quotes` | **是** | 否则就是个免费行情代理 |
  | `GET /api/valuations` | **是** | 单次最多 100 代码 = 100 次 KV 读 |
  | `/api/transactions/*`、`/api/positions`、`/api/xray` | **是** | 用户数据 |

  这张表有个已知的张力：基金详情页是公开的，但它要显示重仓股的实时涨跌，而 `/api/quotes` 要登录。**解法是给公开页面一条受限的专用路由**（比如 `/api/funds/:code/quotes`，只返回该基金重仓股的行情），而不是把 `/api/quotes?secids=` 这个任意 secid 代理开放出去 —— 前者的滥用面是有限的，后者是个免费行情 API。`apps/web/src/lib/api.ts` 里的 `fetchQuotes()` 目前定义了但还没有任何路由在用，改起来不牵扯已有页面。
- **公开路由加基于 KV 的按 IP 限流**，搜索类每 IP 每分钟 30 次，超限返回 429 不要静默降级。
- **持仓从流水推导，`positions_cache` 只是缓存**（architecture.md 已定「交易流水为唯一真相源」）。**不要让接口直接写 `positions_cache`** —— 两条写路径必然开始不一致，而且是静默的。
- **五种流水类型的成本口径全部定死**（`TransactionType` 已有这五种，别自己发明第六种，也别把没定义的行为留给实现去猜）：

  | 类型 | 份额 | 成本总额 | 均价 |
  |---|---|---|---|
  | `SNAPSHOT` | 重置为该值 | 重置为该值 | 随之重置 |
  | `BUY` | 加 | 加（含 `fee`） | 移动加权平均，重算 |
  | `SELL` | 减 | 按**当前均价**减 | **不变** |
  | `DIVIDEND`（现金分红） | 不变 | **减去分红金额** | 随之下降 |
  | `DIVIDEND`（红利再投） | 加 | **不变** | 随之下降 |
  | `CONVERT` | 转出侧按 `SELL`、转入侧按 `BUY` 处理，两侧是两条流水 | | |

  现金分红与红利再投用 `shares` 是否为空区分：有份额就是再投，没有就是现金。**两种分红都不增加成本** —— 分红是本金的返还，把它当成本会让持仓收益率永久性偏低，而且没人会发现。
- **`PENDING` 状态的流水不计入持仓。** 场外基金 T+1 确认，未确认的份额还不是你的。
- **`GET /api/positions` 要把估值一起返回**，别让前端再打一次 `/api/valuations` 拼装 —— 两次请求之间的时间差会让总资产和分项对不上。

### 持仓穿透（P5）

- **覆盖率是返回值里的一等字段，不是附注。** 前十大只覆盖净值 40–70%，不标覆盖率用户会以为那是全部持仓 —— 这是这个功能唯一的伦理风险点。`lib/mock.ts` 的 `MOCK_XRAY_META` 已预留结构，照它的形状返回。
- **敞口金额** = Σ(基金持仓市值 × 该股占该基金净值比)。基金持仓市值用估值还是官方净值，**用了哪个要在 meta 里标明** —— 盘中和盘后的数不一样，用户会发现，不解释就是 bug。
- **报告期取所有持仓基金里最旧的那个**作为整体口径标注，不要取最新的（那会高估数据新鲜度）。
- **文案只陈述事实，不出现「建议」「应该」「优/劣」。** 基金投顾在中国是持牌业务，architecture.md 已把「投资建议」改为「客观指标提示」。要做的三项：7 日内赎回费 1.5% 惩罚提醒、持仓集中度、行业重叠度。

### Notifier（P4）

`cron.ts` 里 `dailyBrief: '0 13 * * 2-6'` 已注册但落在「尚未接入」分支。接口见 [architecture.md](architecture.md#notifier-抽象)。

- **webhook URL 用 AES-GCM 加密存 D1，密钥放 Worker secret `NOTIFY_KEY`。** **你不要创建这个 secret**，那是凭据，由用户自己 `wrangler secret put`。代码要处理「secret 未配置」：明确报错，**不要降级成明文存储**。webhook URL 也不要出现在任何日志或错误信息里。
- **先把 Discord 跑通再写 Telegram 和飞书。** 第一个适配器会暴露接口抽象的问题，那时候改一处比改三处便宜。
  （architecture.md 原本写的是飞书优先，2026-08-12 改成 Discord 优先 —— 用户手上现成有 Discord，且飞书 webhook 端点在境内，从 Cloudflare 出口能不能稳定到达是个未验证的问题，P0 那 30 小时探针测的就是这类事。Discord 是 CF Workers 的成熟路径，先用它把接口抽象磨出来，飞书留到有出口证据之后。）
- **发到用户服务器里的专用频道，不发私聊。** Discord webhook 结构上就只能投递到服务器频道（发不了 DM），所以这条是天然满足的 —— 但**目标频道必须是为这个项目新建的专用频道，不要往已有的聊天频道里塞**。
- **要两个频道、两个 webhook，不是一个：**

  | 频道 | 内容 | 频率 |
  |---|---|---|
  | 日报频道 | 每日 21:00 的持仓日报 | 每交易日一条，约 250 条/年 |
  | 告警频道 | 交易日历将用尽/已用尽、缺输入型 `NONE` 出现、官方净值同步失败、估值整批失败 | 正常情况下**一条都没有** |

  理由就是这个项目反复在用的那条判据（通用判据 4）：**日报是高频、预期之内、不需要行动的；告警是低频、意外、必须马上处理的。混在一个频道里，250 条日报会把那一条真正要命的告警埋掉** —— 而用户要么全都看、要么把整个频道静音，没有中间选项。分开之后，告警频道平时一片安静，一有消息就说明真出事了。

  `NotifyBinding` 要能区分这两个用途（比如带一个 `kind: 'DAILY' | 'ALERT'` 字段），不要写死成一个 webhook。**告警那条链路可以放到最后做，但数据结构现在就要留出位置** —— 事后加会牵动 D1 表结构和所有适配器。
- **Discord 的四个坑，先记下来免得踩：**
  - **成功返回的是 `204 No Content`，不是 200。** 判成功时按 `res.ok` 或显式接受 204，写死 `=== 200` 会让每次成功都被记成失败 —— 然后触发 22:00 补发，于是每天两条。
  - **429 会带 `retry_after`（秒）**，必须读它再重试，不要固定退避。Discord 对单个 webhook 有速率限制，日报这种低频用法正常打不到，但补发逻辑和重试叠在一起就可能。
  - **webhook URL 里就带着 token**（`/api/webhooks/{id}/{token}`），所以它本身是 bearer 凭据，加密存储和「不进日志」这两条同样适用 —— 不要因为「Discord 没有签名校验这个选项」就以为它不敏感。
  - **卡片用 `embeds`**，有长度上限（单条消息的 embed 总量、字段数、description 长度都有限）。**具体数值去查 Discord 官方文档确认，不要照记忆写。** 持仓多的时候会超，超了要**显式说明「另有 N 只未显示」**，不能静默截断 —— 静默丢数据和数据没生成在用户那里长得一样。
- **净值没更新照发，卡片里标注「N 只未更新」。** 「今天没收到日报」和「今天推送挂了」在用户那里长得一样，前者会让人对后者失去警觉。
- **22:00 补发必须先判断 21:00 那次是否真的成功**（用 KV 记当日状态）。不要无条件补发 —— 每天两条一样的日报，两周内用户就会静音这个渠道，那时真出事的告警也一起被静音。（判据 4）
- **`DAILY_BRIEF` 也要走交易日历守卫**，非交易日不发。守卫逻辑 `cron.ts` 已有，加进 task 列表即可。

### pipelines 与其他

- **照 `pipelines/trading_calendar.py` 的模式写**：stdlib 优先、写入前全量校验、校验不过不产出文件、支持离线参数以便无网络测试。要做的三个：全量基金列表、净值历史归档、持仓明细归档，都写 R2（`latest_official_navs` 只存最新值，历史严格放 R2）。可以用 AKShare。
- **每个 pipeline 都要能因为「上游没给出该有的东西」而变红。** 交易日历那次的教训就是可选参数让脚本在该失败的时候成功了。
- **搜索涨跌幅单独取、单独缓存 60 秒，不要塞进搜索结果那个 1 小时 TTL 的缓存对象。** 基金名和代码一小时不变，涨跌幅一分钟就变 —— 变化频率差两个数量级的东西不该共用缓存生命周期。
- 收益归因 / 日收益序列从 `valuation_samples` + `latest_official_navs` 推导，**只做后端数据**。

## 每做完一块的自证要求

**不要攒到最后一起验。** 每完成一块就跑：`npm test`、`npm run typecheck`、`npm run build`，然后做那一块特有的实际验证 —— 不是看代码对不对，是让它真的跑一次：

- **估值 TTL**：部署后在**非交易时段** `curl /api/valuations?codes=...`，应该仍能返回上一次的估值
- **鉴权**：手工插邀请码 → 兑换 → 拿 cookie → POST 一笔流水 → GET 持仓看到它 → **不带 cookie 请求同一路由确认返回 401**（这是安全目标，必须实际验，不能只看代码）
- **持仓推导**：单测覆盖 SNAPSHOT 建仓、追加 BUY 后均价、部分 SELL 后成本、全部卖出归零、PENDING 不计入
- **穿透**：用真实账号插几笔流水，手工拿计算器核对一只股票的敞口金额 —— 别只看它返回了数
- **Notifier**：加解密往返单测 + 用真实 Discord webhook 实际发一条出来看效果。**另外单独验一次「发送失败」的分支** —— 故意用一个失效的 webhook URL，确认它被判成失败（而不是因为 204/200 判错而记成成功），并且 22:00 的补发真的触发
- **pipeline**：故意喂一份残缺输入，确认它**不产出文件**而不是产出一份坏文件

远端 D1 查询要带 `-c .wrangler.generated.toml`：

```
npx wrangler d1 execute lookthru --remote -c .wrangler.generated.toml --command "SELECT ..."
```

仓库里的 `wrangler.toml` 是占位符版本，直接查会报 7400/7403 —— **那不是权限问题**，别去折腾 token。

迁移用 `npm run db:migrate:local` 和 `npm run db:migrate`。

## 需要人做的三件事

你做不了，也不该做：

1. **GitHub Actions secrets** —— 仓库缺 `CLOUDFLARE_API_TOKEN`（R2 Object Read & Write）和 `CLOUDFLARE_ACCOUNT_ID`。没有它们，交易日历的每月刷新和 2027 年自动生成都不会执行，**第一次红会在 2026-09-02 出现**
2. **`NOTIFY_KEY`** —— 做 Notifier 之前 `wrangler secret put NOTIFY_KEY`
3. **两个 Discord webhook** —— 在用户自己的服务器里**新建两个专用频道**（日报 / 告警，理由见 Notifier 那节），各建一个 webhook。路径：频道 → 编辑频道 → 整合 → Webhook → 新建 Webhook → 复制 URL。**URL 里带 token，等于密码**，别写进仓库或 commit，直接给 Codex 或放 `.dev.vars`

碰到这三样就停下来说，不要自己想办法绕过。
